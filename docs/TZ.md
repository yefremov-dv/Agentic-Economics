## 1. Назначение и цели

Agentic Economics — демонстрационная платформа **агентной экономики**: рынка, на котором ИИ-агенты разных компаний конкурируют за выполнение задач пользователей.

Цели первой версии:

1. Показать полный цикл: запрос пользователя → декомпозиция → аукцион между агентами → подтверждение → выполнение → расчёт в виртуальной валюте.
2. Работать через терминал, без веб-интерфейса.
3. Использовать только тестовые (моковые) данные — без реальных бронирований, покупок и платежей.

## 2. Термины

| Термин | Значение |
|---|---|
| Клиент | Физическое лицо, ставящее задачу в чате |
| Провайдер | Юридическое лицо, публикующее агентов-исполнителей |
| Администратор | Управляет каталогом агентов, провайдерами и кошельками |
| Оркестратор | Главный агент: общается с клиентом, декомпозирует задачу, проводит аукционы |
| Агент-исполнитель | Агент провайдера, делающий ставки и выполняющий подзадачи |
| Подзадача | Атомарная задача, сохраняемая в файл `task-N.md` |
| Ставка (bid) | Предложение агента: цена, срок, уверенность, краткое описание решения |
| Эскроу | Сумма, заблокированная на кошельке клиента до выполнения подзадачи |

## 3. Роли и сценарии

### 3.1 Клиент
- Пишет задачу в свободной форме в единую строку чата.
- Отвечает на уточняющие вопросы оркестратора.
- Просматривает план и ставки, подтверждает, отклоняет или просит изменить.
- Получает итоговый результат и видит списания со своего кошелька.

### 3.2 Провайдер (юрлицо)
- Владеет одним или несколькими агентами и счётом в виртуальной валюте.
- В первой версии провайдеров и их агентов заводит администратор. Конструктор агентов — в следующих версиях (раздел 11).

### 3.3 Администратор
- Добавляет, изменяет, отключает агентов и провайдеров (YAML-файлы и CLI).
- Пополняет кошельки, просматривает журнал транзакций и историю аукционов.

## 4. Основной сценарий

Пример запроса:

> Хочу через неделю полететь в Турцию на 6 ночей в отель Maxx Royal Belek, бюджет 1 000 000 рублей. Хочу, чтобы на мне были розовые кроссовки Nike.

```
Клиент ──► Оркестратор
             1. Уточнение (город вылета, число туристов, размер обуви…)
             2. Декомпозиция → tasks/<session_id>/task-1.md … task-N.md
             3. Аукцион по каждой подзадаче
             4. План + ставки + итог vs бюджет ──► Клиент: подтвердить / изменить / отменить
             5. Блокировка суммы (эскроу)
             6. Выполнение подзадач агентами-победителями
             7. Приёмка → перевод провайдерам (минус комиссия)
             8. Итоговый отчёт ──► Клиент
```

Ожидаемая декомпозиция примера:

| # | Подзадача | Категория |
|---|---|---|
| 1 | Авиабилеты туда-обратно (Москва → Анталья), даты | `flights` |
| 2 | Проживание в Maxx Royal Belek, 6 ночей | `hotels` |
| 3 | Трансфер аэропорт ↔ отель | `transfers` |
| 4 | Розовые кроссовки Nike нужного размера с доставкой до вылета | `retail` |
| 5 | Страховка для выезда за рубеж **[уточнить: добавлять ли подзадачи, о которых клиент не просил]** | `insurance` |

## 5. Функциональные требования

### 5.1 Чат (CLI)
- **FR-1.** Интерактивный чат в терминале: `python -m agentic_economics chat --user <id>`.
- **FR-2.** Сессия диалога сохраняется в БД. Её можно продолжить по `--session <id>`.
- **FR-3.** Служебные команды внутри чата: `/plan`, `/bids`, `/balance`, `/history`, `/cancel`, `/help`, `/exit`.
- **FR-4.** Форматированный вывод: таблицы ставок, статусы, суммы. Рекомендуется библиотека `rich`.

### 5.2 Оркестратор
- **FR-5.** Если в запросе не хватает данных для декомпозиции, оркестратор задаёт уточняющие вопросы.
- **FR-6.** Разбивает задачу на **максимальное число простых подзадач**, каждая из которых выполнима одним агентом одной категории.
- **FR-7.** Сохраняет каждую подзадачу в `tasks/<session_id>/task-N.md` (формат в п. 6.1) и в БД.
- **FR-8.** Учитывает зависимости между подзадачами (например, трансфер зависит от рейса и отеля) и выполняет их в правильном порядке.
- **FR-9.** Контролирует бюджет: если сумма лучших ставок превышает бюджет, предлагает альтернативы (более дешёвые ставки, отказ от части подзадач).

### 5.3 Аукцион
- **FR-10.** Отбор кандидатов: по категории подзадачи из активных агентов, затем ранжирование LLM по соответствию описания агента подзадаче. Не более `N` кандидатов (по умолчанию 5).
- **FR-11.** Каждый кандидат получает подзадачу и возвращает ставку в структурированном виде:
  `price`, `currency`, `eta` (срок), `confidence` (0–1), `offer` (что конкретно предлагается, на основе моковых данных).
  Агент может отказаться от участия.
- **FR-12.** Правило выбора победителя по умолчанию: взвешенная оценка
  `score = w_price · (1 − price_norm) + w_conf · confidence + w_rating · rating_norm`,
  веса задаются в конфиге.
- **FR-12a.** Формат аукциона — **один раунд закрытых ставок**: каждый агент делает одну ставку и не видит ставок конкурентов. Переторжки нет. При равенстве `score` побеждает ставка, пришедшая раньше.
- **FR-13.** Таймаут на ставку (по умолчанию 30 с). Не ответивший агент выбывает из аукциона.
- **FR-14.** Все ставки и результат аукциона сохраняются в БД и доступны в `/bids`.

### 5.4 Подтверждение
- **FR-15.** Перед назначением клиенту показывается: список подзадач, победитель и 1–2 альтернативы по каждой, итоговая сумма, комиссия, остаток бюджета и баланса.
- **FR-16.** Действия клиента: `подтвердить всё` / `заменить исполнителя по task-N` / `убрать task-N` / `изменить требования` (новая декомпозиция или аукцион) / `отменить`.
- **FR-17.** Ни одна сумма не блокируется и ни один агент не начинает выполнение без явного подтверждения.

### 5.5 Выполнение
- **FR-18.** Агент-победитель выполняет подзадачу по своему системному промпту и моковым данным из `data/mock/` и возвращает результат (номер брони, рейс, заказ — фиктивные).
- **FR-19.** Оркестратор проверяет результат на соответствие подзадаче. При несоответствии — одна повторная попытка, затем переход ко второму месту аукциона.
- **FR-20.** Статусы подзадачи: `new → bidding → awaiting_approval → approved → in_progress → done | failed | cancelled`.

### 5.6 Виртуальные кошельки
- **FR-21.** Кошельки есть у каждого клиента, каждого провайдера и у платформы. Валюта — виртуальный рубль (`VRUB`).
- **FR-22.** После подтверждения сумма ставки блокируется (эскроу). После успешного выполнения переводится провайдеру за вычетом комиссии платформы. При неудаче или отмене — возвращается клиенту.
- **FR-23.** Комиссия платформы задаётся в конфиге, по умолчанию 5 %. **[уточнить]**
- **FR-24.** Все операции пишутся в журнал транзакций, записи неизменяемы. Баланс вычисляется из журнала (двойная запись).
- **FR-25.** Операция отклоняется, если на балансе клиента недостаточно средств.

### 5.7 Администрирование (CLI)
- **FR-26.** `agent list | show <id> | add <file.yaml> | disable <id> | reload`
- **FR-27.** `provider list | add`
- **FR-28.** `wallet balance <owner> | topup <owner> <amount>`, `ledger [--owner]`
- **FR-29.** `auction show <task_id>` — история ставок.
- **FR-30.** Роль администратора в демо определяется флагом `--admin` или отдельной командой `admin`, без аутентификации. **[уточнить]**

### 5.8 Итоговый отчёт
- **FR-31.** По завершении оркестратор выводит сводку в терминал и сохраняет её в `tasks/<session_id>/result.md`: подзадачи, исполнители, результаты, суммы, итог относительно бюджета.

## 6. Форматы данных

### 6.1 Файл подзадачи `task-N.md`

```markdown
---
id: task-2
session: 2026-09-22-a1b2
category: hotels
depends_on: [task-1]
status: awaiting_approval
budget_hint: 600000
winner: hotel-sunrise
price: 540000
---
# Проживание в Maxx Royal Belek

Даты: 29.09–05.10 (6 ночей), 1 взрослый. Номер категории не ниже Deluxe.

## Критерии выполнения
- Подтверждённая бронь на указанные даты
- Цена ≤ budget_hint
```

### 6.2 Описание агента `agents/<id>.yaml`

```yaml
id: hotel-sunrise
name: "Санрайз Отели — бронирование"
provider: ooo-sunrise-travel
category: hotels
description: "Бронирование отелей Турции и Египта, премиум-сегмент"
system_prompt: |
  Ты агент компании ООО «Санрайз Тревел». Подбираешь и бронируешь отели…
pricing:
  base_markup: 0.07      # наценка к цене из моковых данных
  min_price: 1000
mock_data: data/mock/hotels.json
rating: 4.6
active: true
```

При старте и по `agent reload` файлы валидируются (Pydantic) и синхронизируются с таблицей `agents` в SQLite. Источник истины — YAML. Записи в БД для удалённых файлов помечаются неактивными.

### 6.3 Схема БД (SQLite)

| Таблица | Основные поля |
|---|---|
| `users` | id, name, role (`client` / `admin`) |
| `providers` | id, name, inn (фиктивный) |
| `agents` | id, provider_id, category, description, config_json, rating, active |
| `wallets` | id, owner_type, owner_id, currency |
| `transactions` | id, ts, debit_wallet, credit_wallet, amount, kind (`topup` / `hold` / `release` / `payout` / `fee` / `refund`), task_id |
| `sessions` | id, user_id, created_at, status, budget |
| `messages` | id, session_id, role, content, ts |
| `tasks` | id, session_id, title, category, depends_on, status, winner_bid_id, result_json |
| `bids` | id, task_id, agent_id, price, eta, confidence, offer, score, status |

### 6.4 Моковые данные
`data/mock/` содержит JSON-каталоги: `flights.json`, `hotels.json` (в том числе Maxx Royal Belek), `transfers.json`, `products.json` (в том числе кроссовки Nike разных цветов и размеров), `insurance.json`. Данные правдоподобны, но полностью вымышлены.

### 6.5 Начальный набор агентов (seed)
По **2–3 агента разных провайдеров на каждую категорию**, чтобы аукцион был содержательным. Всего 10–12 агентов в категориях `flights`, `hotels`, `transfers`, `retail`, `insurance`. Провайдеры и их стартовые балансы — в `data/seed.yaml`. Стартовый баланс клиента — 1 500 000 VRUB.

## 7. Архитектура и стек

| Компонент | Технология |
|---|---|
| Язык | Python 3.11+ |
| Агентный фреймворк | LangChain (при необходимости — LangGraph для графа оркестратора) |
| LLM | GigaChat через пакет `langchain-gigachat` |
| Структурированный вывод | Pydantic-модели + `with_structured_output` |
| Хранилище | SQLite (SQLAlchemy или `sqlite3`) |
| CLI | `typer` + `rich` |
| Конфигурация | `config.yaml` + переменные окружения (`.env`) |
| Тесты | `pytest`, LLM подменяется фейковой моделью |

Структура проекта:

```
agentic_economics/
  cli.py            # команды chat / agent / wallet / ledger / auction
  orchestrator/     # диалог, декомпозиция, контроль бюджета
  auction/          # отбор кандидатов, сбор ставок, выбор победителя
  agents/           # базовый класс агента-исполнителя, загрузка YAML
  wallet/           # кошельки, эскроу, журнал
  storage/          # БД и модели
  llm.py            # фабрика GigaChat
agents/             # YAML-описания агентов
data/mock/          # моковые каталоги
tasks/              # файлы task-N.md и result.md (в .gitignore)
tests/
```

Все агенты-исполнители — экземпляры одного класса, параметризованные YAML-описанием (системный промпт, ценовая политика, источник моковых данных). Агент получает доступ к моковым данным через инструменты LangChain (tools), например `search_hotels`.

## 8. Нефункциональные требования

- **NFR-1. Секреты.** Credentials GigaChat только в переменных окружения (`GIGACHAT_CREDENTIALS`, `GIGACHAT_SCOPE`) или в `.env`. `.env` в `.gitignore`, в репозитории — `.env.example`.
- **NFR-2. Устойчивость.** Повтор запросов к LLM при сетевых ошибках (до 3 раз). Некорректный ответ модели (невалидный JSON) не должен ронять сессию.
- **NFR-3. Производительность.** Ставки в аукционе собираются параллельно (asyncio). Полный сценарий из раздела 4 — не дольше 3 минут. **[уточнить]**
- **NFR-4. Наблюдаемость.** Логи в файл `logs/` с уровнем, задаваемым флагом `--verbose`. Флаг `--trace` показывает в терминале рассуждения оркестратора и сырые ставки.
- **NFR-5. Воспроизводимость.** Команда `reset-demo` пересоздаёт БД из seed-данных.
- **NFR-6. Тесты.** Покрытие логики кошельков и выбора победителя аукциона — не ниже 90 %. Сценарный тест полного цикла на фейковой LLM.
- **NFR-7. Язык.** Интерфейс, промпты и отчёты на русском.

## 9. Ограничения первой версии

- Нет реальных API, бронирований, платежей и персональных данных.
- Нет веб-интерфейса и аутентификации.
- Один клиент работает в одной сессии одновременно.
- Агенты провайдеров заводятся только администратором (YAML или CLI).

## 10. Критерии приёмки

1. `pip install -e .`, заполнение `.env` и `reset-demo` поднимают рабочее демо.
2. Запрос из раздела 4 приводит к:
   - уточняющим вопросам (если данных не хватает);
   - созданию не менее 4 файлов `task-N.md` с корректными категориями и зависимостями;
   - аукциону по каждой подзадаче с не менее чем двумя ставками;
   - показу плана и запросу подтверждения до любых списаний;
   - после подтверждения — выполнению подзадач, списаниям и выплатам в журнале, созданию `result.md`.
3. Итоговая сумма не превышает бюджет, либо оркестратор явно сообщает о превышении и предлагает варианты.
4. Сумма всех балансов после сценария равна сумме до него (деньги не создаются и не исчезают).
5. Отказ клиента на шаге подтверждения не вызывает ни одной транзакции, кроме уже существующих.
6. Новый агент, добавленный YAML-файлом и `agent reload`, участвует в следующем аукционе своей категории.
7. Все тесты `pytest` проходят.
